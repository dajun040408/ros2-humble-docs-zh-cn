测试
====

为什么需要自动化测试？
----------------------

以下列出采用自动化测试的许多重要原因：

* **更快地迭代代码。** 你可以更快地对代码进行增量更新。ROS 拥有数百个功能包，而且彼此存在大量依赖关系，因此很难预判一次小修改可能造成的问题。如果修改通过了单元测试，就可以更有信心地认为没有引入问题，或者至少这些问题不是由你的修改造成的。
* **更有信心地重构代码。** 单元测试通过意味着重构过程中没有引入缺陷，使开发者能够更放心地修改代码。
* **改善代码设计。** 单元测试要求代码更容易被测试。这通常意味着将底层函数与框架分离，这也是 ROS 代码的重要设计目标之一。
* **防止缺陷回归。** 对每个修复的缺陷编写单元测试是一种良好实践。事实上，最好先编写测试，再修复缺陷。这样可以精确甚至确定性地重现问题，更清楚地理解问题原因，从而编写更好的补丁。修复后再通过回归测试验证，避免以后修改代码时再次引入同一缺陷，也更容易让审查者相信问题已经解决。
* **让其他开发者更容易使用和修改代码。** 修改代码时，很难判断是否破坏了其他人的功能。单元测试为其他开发者提供验证变更的工具。自动化测试记录代码设计决策，并在这些决策被破坏时自动通知开发者。因此，测试也成为代码文档：大多数时候无需阅读，但当需要检查时，测试系统会准确指出应关注的内容，即哪些测试失败。编写自动化测试能够提高其他贡献者的效率，改善整个 ROS 项目。
* **降低参与 ROS 贡献的门槛。** 对新的外部开发者而言，修改他人的组件往往很困难，因为他们经常只能依靠猜测进行开发。自动化测试框架能够提供即时反馈，使贡献过程更容易，新贡献者也能更容易加入，并提交质量更高的首次贡献，从而降低维护者的工作量。
* **简化维护工作。** 对于变化较慢、主要需要更新依赖项的成熟功能包，自动化测试套件可以快速确认软件包是否仍能正常工作，也更容易判断该功能包是否仍受到支持。
* **放大持续集成的价值。** 回归测试与常规场景测试共同构成组件的自动化测试体系。这样，组件能够更好地应对其依赖 API 的变化，CI 服务器也能更准确地报告代码中出现的问题。

编写测试最重要的价值之一，是让你成为更负责任的项目参与者。测试会在长期内影响软件质量，这是许多开源项目广泛接受的实践。编写回归测试，就是在为 ROS 生态系统的长期质量做贡献。

这些好处是免费的吗？
--------------------

当然，天下没有免费的午餐。要获得测试带来的收益，必须投入一定成本。

* **需要开发测试。** 有时编写测试可能比较困难或成本较高。测试还应当自动化，因此有时并不简单。如果测试依赖特殊硬件，问题会尤其复杂。尽量使用仿真、模拟硬件，或将问题缩小为更小的软件问题；也应避免依赖人工操作等外部环境。
* **回归测试和其他自动化测试需要维护。** 当组件设计发生变化时，许多测试可能失效，例如无法编译，或因 API 设计变化而在运行时抛出异常。这些测试失败不一定意味着重构重新引入了缺陷，也可能只是测试本身需要更新。对于较大的重新设计，有时应删除旧的回归测试。
* **大型测试集可能耗时较长。** 这会增加持续集成服务器的运行成本。
