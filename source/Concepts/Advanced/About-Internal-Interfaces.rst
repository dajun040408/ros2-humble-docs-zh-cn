ROS 2 内部接口
================

.. contents:: 目录
   :local:

.. include:: ../../../global_substitutions.txt

ROS 内部接口是面向开发者公开的 C API，主要供创建客户端库或添加底层中间件实现的开发者使用，并非面向普通 ROS 用户。ROS 客户端库提供了大多数 ROS 用户熟悉的上层 API，并且可以使用多种编程语言实现。

内部 API 架构概述
-------------------

ROS 2 主要包含两种内部接口：

* ROS 中间件接口（``rmw`` API）。
* ROS 客户端库接口（``rcl`` API）。

``rmw`` API 是 ROS 2 软件栈与底层中间件实现之间的接口。ROS 2 使用的底层中间件是 DDS 或 RTPS 实现，负责发现、发布/订阅机制、服务的请求/响应机制，以及消息类型的序列化。

``rcl`` API 是一个更高层次的 API，用于实现客户端库。它不会直接接触中间件实现，而是通过 ROS 中间件接口（``rmw`` API）抽象层访问中间件。

.. figure:: ../images/ros_client_library_api_stack.png
   :alt: ROS 2 软件栈

如图所示，这些 API 采用分层结构。普通 ROS 用户通常使用客户端库 API（例如 ``rclcpp``）编写可执行程序或库。客户端库（例如 ``rclcpp``）的实现使用 ``rcl`` 接口访问 ROS 计算图及其事件。``rcl`` 的实现再通过 ``rmw`` API 访问 ROS 计算图。

``rcl`` 实现的目的是为更复杂的 ROS 概念和实用工具提供通用实现，使不同客户端库能够复用，同时不依赖具体底层中间件。``rmw`` 接口的目的是提取支持 ROS 客户端库所需的最小中间件功能。最后，``rmw`` API 的具体实现由特定中间件实现的功能包提供，例如 ``rmw_fastrtps_cpp``，其库会针对供应商特定的 DDS 接口和类型进行编译。

上图中还有一个标记为 ``ros_to_dds`` 的方框，它代表一类可能存在的功能包。这类功能包允许用户通过 ROS 对应接口访问 DDS 供应商特定的对象和设置。

该抽象接口的目标之一，是让 ROS 用户空间代码完全不受底层中间件影响，从而在更换 DDS 供应商甚至更换中间件技术时，尽可能减少对用户代码的影响。不过，我们也认识到，有时用户确实需要深入实现内部手动调整设置，即使这可能带来一定后果。

通过要求用户使用专门的功能包访问底层 DDS 供应商对象，可以避免在常规接口中暴露供应商特定的符号和头文件。同时，也可以通过检查功能包依赖关系，识别可能破坏供应商可移植性的代码。

.. _Type Specific Interfaces:

特定类型接口
--------------

在整个接口栈中，有些 API 必然与正在交换的消息类型有关，例如发布消息或订阅话题，因此需要为每种消息类型生成代码。

下图展示了从用户定义的 ``rosidl`` 文件（例如 ``.msg`` 文件）到用户和系统执行特定类型操作时所使用的类型专用代码的生成路径。

.. figure:: ../images/ros_idl_api_stack_static.png
   :alt: ROS 2 IDL 静态类型支持栈

   图：从 rosidl 文件到用户接口代码的“静态”类型支持生成流程。

图的右侧展示了如何将 ``.msg`` 文件直接传递给特定语言的代码生成器，例如 ``rosidl_generator_cpp`` 或 ``rosidl_generator_py``。这些生成器负责创建用户需要 include 或 import 的代码，并将其作为消息在内存中的表示形式。

例如，对于消息 ``std_msgs/String``，C++ 用户可以使用：

.. code-block:: cpp

   #include <std_msgs/msg/string.hpp>

Python 用户则可以使用：

.. code-block:: python

   from std_msgs.msg import String

这些语句之所以能够工作，是因为相应的语言专用（但与中间件无关）生成器功能包生成了对应文件。

此外，``.msg`` 文件还会用于为每种类型生成类型支持代码。这里的类型支持是指与特定类型相关的元数据或函数，系统利用这些信息执行该类型所需的特定任务。某种消息的类型支持可能包含消息中每个字段的名称和类型列表，也可能包含执行特定任务（例如发布消息）的代码引用。

.. _internal-interfaces_static-type-support:

静态类型支持
^^^^^^^^^^^^^^

当类型支持引用某些代码来执行特定消息类型的功能时，这些代码有时需要执行中间件相关工作。

例如，考虑某种消息类型的发布函数：使用“供应商 A”时，该函数需要调用“供应商 A”的 API；使用“供应商 B”时，则需要调用“供应商 B”的 API。

为了允许使用中间件供应商专用代码，用户定义的 ``.msg`` 文件可能会生成供应商专用代码。这些供应商专用代码仍然通过类型支持抽象层对用户隐藏，其方式类似于“私有实现”（Pimpl）设计模式。

基于 DDS 的静态类型支持
^^^^^^^^^^^^^^^^^^^^^^^^^

对于基于 DDS 的中间件供应商，尤其是那些根据 OMG IDL 文件（``.idl`` 文件）生成代码的供应商，用户定义的 ``rosidl`` 文件（``.msg`` 文件）会先转换为等效的 OMG IDL 文件。

随后，系统根据这些 OMG IDL 文件生成供应商专用代码，并在特定类型的类型支持所引用的函数中使用这些代码。

上图左侧展示了这一过程：``.msg`` 文件由 ``rosidl_dds`` 功能包处理并生成 ``.idl`` 文件，然后将这些 ``.idl`` 文件交给特定语言和 DDS 供应商专用的类型支持生成器。

例如，Fast DDS 实现中包含 ``rosidl_typesupport_fastrtps_cpp`` 功能包。该功能包负责生成相关代码，例如将 C++ 消息对象转换为序列化字节缓冲区，以便通过网络发送。尽管这些代码专用于 Fast DDS，但由于类型支持抽象层的存在，用户仍然无法直接看到它们。

.. _internal-interfaces_dynamic-type-support:

动态类型支持
^^^^^^^^^^^^^^

另一种实现类型支持的方法，是为话题发布等操作提供通用函数，而不是针对每种消息类型都生成一个函数版本。

为实现这一点，通用函数需要获得正在发布的消息类型的元信息，例如该消息类型中各字段的名称、类型和排列顺序。发布消息时，调用通用发布函数，并同时传入待发布消息以及包含必要元数据的结构体。

这种方式称为“动态”类型支持；与之相对，“静态”类型支持需要为每种类型生成对应函数。

.. figure:: ../images/ros_idl_api_stack_dynamic.png
   :alt: ROS 2 IDL 动态类型支持栈

   图：从 rosidl 文件到用户接口代码的“动态”类型支持生成流程。

上图展示了从用户定义的 ``rosidl`` 文件到生成用户接口代码的流程。它与静态类型支持的流程非常相似，区别仅在于类型支持的生成方式，这部分由图的左侧表示。

在动态类型支持中，``.msg`` 文件会直接转换为面向用户的代码。该代码同样与中间件无关，因为其中只包含消息元信息。真正执行操作的函数（例如向话题发布消息）与具体消息类型无关，并会根据需要调用中间件专用 API。

请注意，与静态类型支持由 DDS 供应商专用功能包提供类型支持代码不同，动态类型支持会为每种语言提供与中间件无关的功能包，例如 ``rosidl_typesupport_introspection_c`` 和 ``rosidl_typesupport_introspection_cpp``。``introspection`` 表示能够利用消息类型生成的元数据，对任意消息实例进行内省。这是实现“发布消息”等通用函数的基础能力。

这种方法的优点是，所有生成代码都与中间件无关，只要不同中间件实现支持动态类型支持，就可以复用这些代码。此外，它生成的代码更少，因此可以缩短编译时间并减小代码体积。

不过，动态类型支持要求底层中间件也支持类似形式的动态类型支持。对于 DDS，需要 DDS-XTypes 标准支持使用元信息而不是生成代码来发布消息。底层中间件必须支持 DDS-XTypes 或类似机制，才能提供动态类型支持。

此外，与静态类型支持相比，这种类型支持方式通常速度更慢。静态类型支持中的特定类型生成代码可以更加高效，因为它不需要遍历消息类型的元数据来执行序列化等操作。

rcl 仓库
----------

ROS 客户端库接口（``rcl`` API）可供客户端库使用，例如 ``rclc``、``rclcpp``、``rclpy`` 等，以避免重复实现逻辑和功能。

通过复用 ``rcl`` API，客户端库可以更小，并且彼此之间具有更一致的行为。客户端库中的某些部分会有意排除在 ``rcl`` API 之外，因为这些部分应当使用符合具体语言习惯的方式实现。一个典型例子是执行模型，``rcl`` 完全不涉及执行模型，而是由客户端库提供符合语言习惯的解决方案，例如 C 中的 ``pthreads``、C++11 中的 ``std::thread``，以及 Python 中的 ``threading.Thread``。

通常，``rcl`` 接口提供的函数既不依赖特定语言模式，也不依赖特定消息类型。

``rcl`` API 位于 GitHub 的 `ros2/rcl <https://github.com/ros2/rcl>`__ 仓库中，接口以 C 头文件形式提供。同一仓库中的 ``rcl`` 功能包提供 ``rcl`` 的 C 语言实现。该实现不会直接访问中间件，而是使用 ``rmw`` 和 ``rosidl`` API。

完整的 ``rcl`` API 定义请参阅 `rcl 文档 <http://docs.ros.org/en/{DISTRO}/p/rcl/>`__。

rmw 仓库
----------

ROS 中间件接口（``rmw`` API）是构建 ROS 中间件所需的最小原始能力集合。不同中间件实现的提供者必须实现该接口，才能支持其上的完整 ROS 软件栈。目前，大多数中间件实现针对不同 DDS 供应商。

``rmw`` API 位于 GitHub 的 `ros2/rmw <https://github.com/ros2/rmw>`__ 仓库中。``rmw`` 功能包包含定义接口的 C 头文件，具体实现则由面向不同 DDS 供应商的 RMW 实现功能包提供。

完整的 ``rmw`` API 定义请参阅 `rmw 文档 <http://docs.ros.org/en/{DISTRO}/p/rmw/>`__。

有关 ROS 2 如何集成不同中间件实现的实践性深入介绍，请参阅 :doc:`中间件实现教程 <../../Tutorials/Advanced/Creating-An-RMW-Implementation>`。

rosidl 仓库
-------------

``rosidl`` API 由一些与消息相关的静态函数和类型组成，同时定义了不同语言的消息应生成哪些代码。

该 API 指定的消息生成代码与语言相关，但不一定会复用其他语言的生成代码。生成代码包含消息数据结构、构造和析构函数等内容。该 API 还提供获取消息类型支持结构的方法，发布或订阅该消息类型的话题时会使用这一结构。

有多个代码仓库参与 ``rosidl`` API 和实现。

GitHub 上的 `ros2/rosidl <https://github.com/ros2/rosidl>`__ 仓库定义消息 IDL 语法，即 ``.msg``、``.srv`` 等文件的语法，并包含用于解析这些文件、提供 CMake 代码生成基础设施、生成与具体实现无关的代码（头文件和源文件），以及建立默认生成器集合的功能包。

该仓库包含以下功能包：

* ``rosidl_cmake``：提供从 ``rosidl`` 文件（例如 ``.msg``、``.srv``）生成代码所需的 CMake 函数和模块。
* ``rosidl_default_generators``：定义默认生成器列表，确保这些生成器作为依赖项安装；也可以使用其他注入的生成器。
* ``rosidl_generator_c``：提供从 ``rosidl`` 文件生成 C 头文件（``.h``）的工具。
* ``rosidl_generator_cpp``：提供从 ``rosidl`` 文件生成 C++ 头文件（``.hpp``）的工具。
* ``rosidl_generator_py``：提供从 ``rosidl`` 文件生成 Python 模块的工具。
* ``rosidl_parser``：提供用于解析 ``rosidl`` 文件的 Python API。

其他语言的生成器（例如 ``rosidl_generator_java``）托管在外部代码仓库中，但会使用上述生成器相同的机制，将自身注册为 ``rosidl`` 生成器。

除了用于解析 ``rosidl`` 文件并生成头文件的功能包外，``rosidl`` 仓库还包含与文件中定义的消息类型“类型支持”相关的功能包。

类型支持是指解释和操作特定类型 ROS 消息实例所表示信息的能力，例如发布消息。类型支持既可以由编译时生成的代码提供，也可以在运行时根据 ``rosidl`` 文件（例如 ``.msg`` 或 ``.srv`` 文件）的内容以及接收到的数据，通过内省方式以编程形式提供。

对于后者，即通过运行时解释消息来实现类型支持的情况，ROS 2 生成的消息代码可以不依赖具体 RMW 实现。通过数据内省提供类型支持的功能包包括：

* ``rosidl_typesupport_introspection_c``：提供支持 ``rosidl`` 消息数据类型的 C 代码工具。
* ``rosidl_typesupport_introspection_cpp``：提供支持 ``rosidl`` 消息数据类型的 C++ 代码工具。

如果需要在编译时生成类型支持，而不是通过程序动态生成，则必须使用特定于 RMW 实现的功能包。这是因为某个 RMW 实现通常要求以 DDS 供应商特定的方式存储和操作数据，以便 DDS 实现能够使用这些数据。更多信息请参阅上文 :ref:`特定类型接口 <Type Specific Interfaces>`。

rcutils 仓库
--------------

ROS 2 C Utilities（``rcutils``）是一个 C API，由整个 ROS 2 代码库使用的宏、函数和数据结构组成。

这些内容主要用于错误处理、命令行参数解析和日志记录。它们不专属于客户端层或中间件层，因此可以由两者共享。

``rcutils`` API 及其实现位于 GitHub 的 `ros2/rcutils <https://github.com/ros2/rcutils>`__ 仓库中，接口以 C 头文件形式提供。

完整的 ``rcutils`` API 定义请参阅 `rcutils 文档 <https://docs.ros.org/en/{DISTRO}/p/rcutils/>`__。
