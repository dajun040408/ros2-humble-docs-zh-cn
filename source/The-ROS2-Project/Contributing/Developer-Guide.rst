ROS 2 开发者指南
================

.. contents:: 目录
   :depth: 2
   :local:

本页面定义 ROS 2 开发过程中采用的实践和政策。

.. _general-principles:

通用原则
--------

以下原则适用于所有 ROS 2 开发工作：

* **共同所有权：** 每个参与 ROS 2 工作的人都应对系统的所有部分拥有主人翁意识。某段代码的原作者并不拥有该代码的特殊控制权，也不承担唯一维护义务。任何人都可以提出修改、处理任意类型的任务，并审查任何 Pull Request。
* **愿意承担任何工作：** 作为共同所有权的延伸，每个人都应愿意承担可用任务，并为系统的任何部分做出贡献。
* **主动寻求帮助：** 如果遇到困难，应通过 Issue、评论或电子邮件等适当方式向其他开发者寻求帮助。

质量实践
--------

软件包可以根据其遵循的开发实践归入不同质量等级，具体参阅§REP 2004：软件包质量类别 <https://reps.openrobotics.org/rep-2004/>§_。不同类别在版本管理、测试、文档等方面具有不同要求。

以下部分列出确保 ROS 2 核心软件包达到最高质量（Level 1）的具体开发规则。建议所有 ROS 开发者尽量遵循这些政策，以提升整个 ROS 生态系统的质量。

更具体的代码建议请参阅 :doc:§质量指南 <Quality-Guide>§。

生成式 AI 的使用
^^^^^^^^^^^^^^^^

向 ROS 代码或文档提交任何类型的贡献时，都必须遵循§OSRF 关于在贡献中使用生成式工具和生成式 AI 的政策 <https://osralliance.org/wp-content/uploads/2025/05/OSRF-Policy-on-the-Use-of-Generative-Tools-Generative-AI-in-Contributions.pdf>§_。

该政策适用于使用基于现有人类创作内容训练的模型，自动生成贡献中任何部分的工具。不适用于通过标准算法生成内容的工具，也不适用于使用适当授权内容库的工具。

.. _semver:

版本管理
^^^^^^^^

ROS 2 使用§语义化版本控制规范 <http://semver.org/>§_（semver）。

此外，还遵循一些 ROS 专用规则：

* 已发布的 ROS 发行版中，不应增加主版本号（即不应引入破坏性变更）。
* 补丁版本（保持接口不变）和次版本（不破坏兼容性）的变更可以在发行版生命周期内进行。
* 对公共 API 或 ABI 的修改必须经过审查，并明确说明兼容性影响。

代码审查与 Pull Request
-----------------------

所有代码变更都应通过 Pull Request 提交，并由其他开发者审查。贡献者应确保 PR 范围清晰、测试充分，并遵循相应代码风格。

持续集成
--------

提交到 ROS 2 核心仓库的变更应通过持续集成测试。CI 用于验证代码能够在受支持平台和配置上构建、测试，并保持项目质量。

测试
----

新功能和缺陷修复应包含适当测试。测试应覆盖正常行为、边界条件和错误处理。对于影响多个软件包的变更，应考虑增加集成测试。

文档
----

代码变更应同步更新相关文档，包括 API 文档、教程和发行说明。文档应准确反映实际行为，并提供可复现的示例。
